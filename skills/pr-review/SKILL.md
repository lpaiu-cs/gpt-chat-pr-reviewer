# PR 리뷰 요청

로컬에서 도는 리뷰 데몬에 "이 PR 을 리뷰해줘" 를 요청하고, 결과가 게시되면
깨어나서 대응한다. 리뷰는 GitHub 에 인라인 코멘트로 올라온다.

모든 명령은 이 스크립트 하나를 지난다:

```
node "{{DAEMON}}" <동사> [인자]
```

## 절차

**1. 요청** — 데몬 기동까지 알아서 한다 (이미 돌고 있으면 그냥 붙는다).

```bash
node "{{DAEMON}}" review owner/repo#12
```

데몬을 **새로 띄웠다면** 출력에 대시보드 주소와 종료 방법이 나온다.
그 안내를 사용자에게 **그대로 전달한다** — 데몬은 세션이 끝나도 계속 돌고,
끄는 건 사용자만 할 수 있다.

데몬이 **관측 모드**(`--observe`)로 떠 있으면 리뷰가 실행되지 않는다. 그때는
명령이 그 사실을 알리고 멈춘다 — **재시작하지 말고** 사용자에게 보고한다.

그 PR 이 감시 범위 밖이면 명령이 그 사실을 알리고 멈춘다. **범위를 넓히지 말고**
사용자에게 전달한다 — 범위는 레포 단위라, 넓히면 그 레포의 다른 열린 PR 까지
리뷰 대상이 되기 때문이다.

**2. 대기** — 반드시 **백그라운드로** 실행한다 (Bash 도구의 `run_in_background`).
앞에서 기다리면 2~15분 동안 아무것도 못 한다.

`review` 출력이 알려준 `wait` 명령을 **그대로** 쓴다:

```bash
node "{{DAEMON}}" wait owner/repo#12 --since-seq 7
```

`--since-seq` 는 요청 시점의 기준값이다. 이게 없으면 **이전 라운드가 남긴
상태**(예: 1차의 `AWAITING_AUTHOR`)를 이번 요청의 결과로 오인해 즉시 깨어난다.
직접 지어내지 말고 `review` 가 낸 값을 그대로 쓴다.

이벤트 하나를 받으면 종료한다. 즉 **이 명령이 끝났다 = 확인할 게 생겼다.**
대기하는 동안 사용자의 다른 요청을 계속 처리한다.

**3. 결과 처리** — 출력 첫 낱말이 이벤트다.

| 이벤트 | 뜻 | 할 일 |
|---|---|---|
| `posted` | 지적 사항이 인라인 코멘트로 게시됨 | 읽고 대응 → **4번(스레드 답변·resolve)까지 반드시** |
| `converged` | approve — 더 지적할 것 없음 | 사용자에게 알린다 |
| `failed` | 라운드 실패 (파싱 실패·리뷰 거부 등) | 데몬이 자동 재시도한다. 반복되면 사용자에게 알린다 |
| `quota` | ChatGPT 대화 한도 도달 | 쿨다운(기본 3시간) 후 자동 재개. 사용자에게 알린다 |
| `closed` | PR 이 닫히거나 머지됨 | 대기 종료 |
| `timeout` | 지정 시간 안에 아무 일도 없었음 | `status` 로 현황 확인 |

**4. 스레드 답변 + resolve** — **순서가 중요하다.**

```
1) 코드 수정 → git commit      (아직 push 하지 않는다)
2) 스레드에 답변 + 고친 것만 resolve   (커밋 해시를 인용할 수 있다)
3) git push
```

**push 를 마지막에 하는 이유.** 상태 머신은 **새 커밋 하나만으로**
`AUTHOR_RESPONDED` 를 발화하고 watch 는 기본 10초 주기로 폴링한다. push 를
먼저 하면 답변을 쓰는 동안 다음 라운드가 시작될 수 있고, 그 프롬프트는
**답변이 없는 스레드**를 읽는다 — 이 절차가 막으려던 바로 그 상황이다.
커밋만 해두면 해시를 답변에 인용하면서도 그 창을 만들지 않는다.

```bash
# 열려 있는 스레드 목록 (스레드 id · 첫 코멘트 id · 제목)
gh api graphql -f query='
query { repository(owner:"OWNER", name:"REPO") { pullRequest(number:N) {
  reviewThreads(first:60) { nodes { id isResolved
    comments(first:1){ nodes { databaseId body } } } } } } }' \
  --jq '.data.repository.pullRequest.reviewThreads.nodes[]
        | select(.isResolved | not)
        | "\(.id)\t\(.comments.nodes[0].databaseId)\t\(.comments.nodes[0].body|split("\n")[0])"'

# 각 스레드에 답변 (무엇을 어떻게 고쳤는지 + 커밋 해시)
gh api repos/OWNER/REPO/pulls/N/comments/<comment_id>/replies -f body='반영했습니다 (abc1234). ...'

# 그리고 resolve
gh api graphql -f query='mutation {
  resolveReviewThread(input:{threadId:"<thread_id>"}) { thread { isResolved } } }'
```

건수가 많으면 위 세 단계를 스크립트로 묶어 한 번에 돈다.

**왜 생략하면 안 되는가**

- 다음 라운드 프롬프트에 **이전 라운드 스레드 현황**이 들어간다. 답변이 없으면
  리뷰어는 무엇이 반영됐는지 모른 채 같은 지적을 다시 올린다.
- 상태 머신이 `AUTHOR_RESPONDED` 를 **새 커밋 또는 전체 resolve** 로 판정한다.
  resolve 는 "이 지적은 끝났다" 는 신호다.

**resolve 는 실제로 고친 스레드에만 한다.**

반영하지 않기로 한 지적은 **이유만 답변하고 열어 둔다.** resolve 는 "대응이
끝났다" 는 선언인데, 반영하지 않기로 한 것은 아직 합의되지 않은 이견이다.
내가 닫아버리면 리뷰어도 사용자도 그 판단을 다시 볼 기회를 잃는다 — 그리고
그 판단은 내가 틀렸을 수 있는 쪽이다.

열어 두면 다음 라운드 프롬프트에 그대로 실려 리뷰어가 재반박하거나 수긍할 수
있고, 사람이 최종 판단을 내릴 수 있다. 진행이 막히지도 않는다 —
`AUTHOR_RESPONDED` 는 새 커밋으로도 발화하므로 다음 라운드는 정상적으로 돈다
(스레드 카운트만 `n/n` 에 못 미친 채 남는다. 그게 "아직 열린 이견이 있다" 는
정확한 표시다).

대응 커밋을 push 하면 데몬이 새 커밋을 감지해 **다음 라운드를 자동으로 돈다.**
`status --pr <ref> --json` 의 `seq` 를 읽어 그 값으로 다시 `wait` 를 건다.
approve 가 날 때까지 이 왕복이 반복된다.

## 그 밖의 동사

```bash
node "{{DAEMON}}" status --pr owner/repo#12   # 현재 상태·라운드·스레드
node "{{DAEMON}}" skip owner/repo#12          # 이 PR 은 리뷰하지 않는다
```

## 하지 말 것

이 데몬은 **여러 세션이 함께 쓴다.** 다른 세션도 자기 PR 의 리뷰를 기다리고 있다.

- **데몬을 끄거나 재시작하지 않는다.** 이 스크립트에 그 동사는 없다.
  사용자가 종료를 원하면 대시보드의 종료 버튼이나 `npm run dev -- stop` 을 안내한다.
- **감시 범위·필터를 바꾸지 않는다.** `scope-set` · `only-set` 같은 전역 설정을
  HTTP 로 직접 부르지 않는다. 한 세션이 "내 PR 만" 을 걸면 다른 세션의 PR 이
  큐에서 사라지고, 범위를 넓히면 요청하지 않은 PR 에 리뷰가 게시된다.
- **일시정지하지 않는다.** 전역이라 모두의 리뷰가 멈춘다.
- PR 이 필터에 걸려 제외돼 있으면 `review` 가 그 사실을 알리고 멈춘다.
  **필터를 풀지 말고** 사용자에게 보고한다.

## 주의

- 리뷰는 **직렬**이다 (브라우저 페이지가 하나). 큐가 밀려 있으면 순서를 기다린다.
- 데몬이 안 뜨면 ChatGPT 로그인이 만료됐을 수 있다 — 이건 사람이 해야 한다.
  출력에 나온 로그 경로와 `npm run setup` 을 안내한다.
