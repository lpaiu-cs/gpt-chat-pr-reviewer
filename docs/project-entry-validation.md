# v0.4.0 프로젝트 진입 검증

2026-09-10 Windows / 시스템 Chrome / 저장된 자동 리뷰 프로필에서 검증했다.

## 변경한 진입 UX

1. `setup`은 브라우저 창을 열고 로그인 계정을 표시한다.
2. 사용자가 리뷰 프로젝트를 만들거나 열고, 사이드바에 고정한 뒤 터미널에서 Enter를 누른다.
3. 열린 프로젝트의 이름과 URL을 읽고, 홈에서 다시 자동으로 진입해 본 뒤에만 저장한다.
4. 자동 리뷰는 창 없는 Chrome으로 실행한다. 이름은 프로젝트 탐색에 사용하고 도착 URL의 ID로 신원을 확인한다.
5. `project-check --repeat 5`는 리뷰를 전송하지 않고 실제 작업 탭 생성·진입·정리를 반복한다.

구버전 설정의 `headless: false`는 자동으로 덮어쓰지 않는다. 창 없는 실행을 원하면 `true`로 바꾸고 `project-check`로 확인한다. URL만 저장된 설정에는 setup을 통한 이름 등록이 필요하다.

## 관측과 선택

- 일반 Chrome과 인앱 브라우저 모두 프로젝트 URL의 전체 문서 로딩에서 실패했다. 일반 Chrome에서는 동일 URL에 사이드바로 이동하면 성공했다. 서버 내부 원인은 확정하지 않았다.
- 호버 상태에 따라 pointer-events가 바뀌는 프로젝트 홈 버튼은 포인터 클릭이 불안정했다. 버튼의 Enter 동작으로 화면 내부 이동을 실행한다.
- 창을 표시하는 Chrome은 기동 시 Windows 포커스를 가져갔다. `--start-minimized`도 이를 막지 못해 채택하지 않았다.
- 헤드리스 기본 UA에서는 같은 프로필의 로그인 확인과 홈 로딩이 실패했다. 설치된 Chrome의 UA에서 `HeadlessChrome/`만 `Chrome/`으로 맞춘 뒤 성공했다. 버전이나 계정 정보를 하드코딩하지 않는다. 처음 탭·작업 탭·복구 탭에 동일한 준비 절차를 적용한다.
- 일반 Chrome과 자동화 Chrome의 계정이 달랐다. 같은 용도의 프로젝트라도 ID가 달랐으며 자동화는 원래 계정과 프로젝트를 유지했다.

## 실제 드라이버 결과

창 없는 실행에서 기존 탭 재진입 5/5와 작업 탭 생성 후 진입 5/5가 성공했다.
최종 작업 탭 검증의 진입 시간은 4,869 / 3,432 / 3,720 / 3,330 / 3,367 ms였다.
매번 프로젝트 ID와 이름, 빈 새 채팅 입력창을 확인하고 작업 탭을 닫았다.

Windows `GetForegroundWindow`와 `GetGUIThreadInfo`를 25 ms sleep으로 표본 수집했다.
실제 간격은 스케줄링을 포함해 약 32 ms였다. 기동·탭 생성·진입·종료를 포함한 두 번의 60초 측정에서
각각 1,911개 / 1,871개 표본 모두 사용자 앱의 동일 활성 창과 키보드 포커스를 유지했다.
표본 간격보다 짧은 변화를 완전히 배제하는 측정은 아니다.

로컬 원본은 `data/diagnostics/focus-headless-success.json`, `focus-workers-success.json`과 `focus-probe.ps1`에 있다.

## 회귀 검증과 범위

- `npm test`: 99/99. 실제 Chrome 격리 페이지에서 전체 로딩 금지, 호버 비활성 버튼의 Enter 동작, setup 등록·재진입, 기존 대화 복귀, 다른 프로젝트 ID 거부, 작성 중인 초안 보존을 검증했다.
- `npm run smoke`: 337/337. 빌드·스킬 설치 스모크·diff 검사 통과.
- 실제 ChatGPT 프롬프트 전송이나 GitHub 리뷰 게시를 이 진입 검증에 포함하지 않았다.
- 같은 이름의 프로젝트가 여럿이거나 사이드바에 없으면 자동으로 다른 프로젝트를 고르지 않고 setup 안내와 함께 실패한다.
- 대화 복귀 시 목록 확장은 최대 10회다. 찾지 못한 대화는 기존 정책에 따라 새 대화로 회전한다.
