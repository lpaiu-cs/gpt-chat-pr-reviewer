# Chrome 프롬프트 입력 지연 — 관측과 후속 수정

## 2026-09-22: 대용량 diff의 전송 거부와 프로젝트 초안 잔류

- 실행 중 데몬은 `node --import tsx .../src/cli.ts serve --ui --no-open`이었다. `platelog#1`의 1,670,342자 입력 검증은 통과했으나 전송 버튼이 10초 후 타임아웃됐다. 이후 같은 프로젝트의 `osk-system#73`, `#74`도 남은 초안 때문에 진입하지 못했다.
- 데몬을 정상 종료한 뒤 동일 프로필에서 초안을 확인·보존했다. 전송 버튼은 HTML `disabled` 속성 없이 `aria-disabled="true"`였고 Playwright trial click도 `element is not enabled`로 실패했다. 초안은 1,660,574자로 복원됐다. 서비스의 정확한 글자 제한은 측정하지 않았다.
- 미전송 초안을 비운 뒤 같은 내용을 텍스트 파일로 첨부하자 파일 처리 완료와 전송 버튼 활성화를 확인했다. 이 진단에서는 메시지를 보내지 않았고 진단 첨부와 입력도 제거했다.
- 고정 diff가 100,000자를 넘으면 전체 UTF-8 원문을 `.txt` 첨부로 전달한다. 이는 편집기 부하를 피하는 전환점이며 서비스 제한값이 아니다. 프롬프트의 PR·라운드·고정 head/merge-base는 유지하고, 파일 전체를 검토할 수 없으면 `ACCESS_FAILED`를 요구한다. 첨부를 잘라내거나 일부 검토를 승인으로 처리하지 않는다.
- 입력 이후 업로드·클릭·전송 확인 실패에서도 자기 입력과 첨부를 회수한다. 이미 생성 중이거나 새 사용자 메시지가 생겼거나 입력이 편집됐으면 지우지 않는다. 기존 초안/첨부는 전송 전에 거부한다. 첨부는 이름 표시뿐 아니라 처리 완료 아이콘을 기다리며, 실패 시 전송하지 않는다.
- 회귀 검증은 `tests/chatgpt-send.test.ts`(Chrome의 전송 실패·첨부·초안 보호)와 `tests/review-boundaries.test.ts`(대용량 diff 원문 보존·SHA 고정)에 있다.
- 실제 1,799,491바이트 diff로 첨부 경로를 추가 검증했다. 97자 파일명에서 카드 생성 실패를 관측한 뒤 이름을 41자로 줄였을 때는 약 15초에 완료됐으나, 이름 축소만으로는 데몬 재실행에서 해결되지 않았다. 서비스의 정확한 파일명 제한이나 내부 실패 원인은 확정하지 않았다. 전체 SHA는 프롬프트에 보존한다.
- 파일을 먼저 선택하고 처리 완료를 기다린 뒤 프롬프트를 입력하도록 순서를 고쳤다. 동일 파일명·내용으로 약 11초에 첨부를 완료했고, 입력 후에도 카드가 남아 있는지 재확인한 뒤 전송 버튼 활성화를 검증했다. 진단은 trial click만 사용했다.
- 첨부는 현재 입력창의 파일 메뉴에서 선택하고, 제거는 카드 hover 후 제거 버튼 클릭으로 한다. 전송 단축키와 겹치는 Enter를 제거 수단으로 쓰지 않는다.
- 원래 초안 때문에 막혔던 `osk-system#73`, `#74`는 수정본에서 응답 수신과 인라인 리뷰 게시까지 완료했다.
- 최종 데몬에서 `platelog#1`의 1,799,491바이트 첨부가 10,566ms에 완료됐고, 3,640자 프롬프트 검증·전송 확인·프로젝트 대화 URL 저장 후 응답 대기로 진입했다. 이 확인 시점에는 아직 리뷰 결과를 받지 않았다. 최종 `npm test` 109/109, `npm run smoke` 337/337, build 및 `git diff --check` 통과.

## 후보와 별도 결함

`src/chatgpt.ts`의 `fillPrompt`는 전체 텍스트를 `keyboard.insertText`로 먼저 삽입한다. 설치된 Playwright의 Chromium 구현은 CDP `Input.insertText`로 연결된다. `locator.fill`도 contenteditable 입력에서 같은 경로를 쓰므로 단순 교체만으로 해결된다고 볼 수 없다.

[Playwright 조사 기록](https://github.com/microsoft/playwright/issues/33761#issuecomment-2503341123)은 다중 줄 Input.insertText에서 줄마다 레이아웃 재계산이 발생한다고 설명한다. 이번 사건의 유력 후보이나 실제 탭 성능 trace로 확정하지 않았다.

- 합성 paste의 `dispatchEvent` 반환값을 성공으로 해석하는 결함: 편집기가 내용을 넣고 preventDefault하면 false다. ProseMirror 구현도 이 패턴이다. EventTarget 최소 재현으로 확인했으나 이번 실행에서 폴백 로그는 없었다.
- 마지막 `keyboard.type(text, {delay: 1})` 폴백은 긴 텍스트에서 대량 이벤트와 중복 입력 위험이 있다.
- `inputHasText`는 비어 있지 않은지만 확인한다. 전체 내용 일치를 검증하지 않는다.
- `clickSend`는 중복 셀렉터 후보와 개별 클릭 대기, 조용히 삼키는 오류가 있어 실제 정체 위치를 구분하기 어렵다.

## 후속 수정과 검증

- 대량 `Input.insertText` 대신 편집기의 paste 트랜잭션을 먼저 사용한다. ProseMirror clipboard HTML에 hard break를 넣어 연속 개행과 들여쓰기를 보존한다. 문자열은 HTML escape한다.
- 이벤트 반환값 대신 전체 내용을 비교한다. CRLF 및 마지막 개행 하나의 렌더링 차이만 정규화하며, 부분 입력 위에 재입력하지 않는다. 빈 입력에 한해 4,000자·80줄 이하만 insertText로 폴백한다. 글자별 타이핑은 제거했다.
- 전송 버튼 후보는 하나의 10초 대기 예산을 공유하고 중지 버튼은 제외한다. 성공 여부를 모르는 Enter 재시도는 제거했다.
- 입력 길이·줄 수, 포커스/paste/검증/클릭/전송 확인 시간과 탭 crash 이벤트를 기록한다. 10초 경고는 실행 중 작업을 중단하거나 겹쳐 재시도하지 않는다.
- 회귀 테스트: `npm test`, 92/92 통과. 성공한 preventDefault paste, 부분 입력, 대량 입력의 폴백 금지, 짧은 입력 폴백 검증.
- 격리 Chrome 152.0.7977.83 + ProseMirror view 1.42.3 / basic schema에서 91,203자·7,201줄 입력 224ms (paste 61ms). 한글·HTML 특수문자·연속 개행·반복 공백을 포함한 내부 문서가 원문과 정확히 일치했다. 중지 버튼 옆의 전송 버튼만 클릭됨을 확인했다.
- 이 수치는 로컬 편집기 실험이다. 기존 실제 ChatGPT 측정과 동일 조건의 전후 비교가 아니며, 실서비스에서의 개선율이나 문제 해결 완료를 뜻하지 않는다. 실행 중 공유 데몬에는 아직 이 변경을 적용하지 않았다.

## 실제 적용 후 확인

### PR #36 1차 리뷰 후 보완

[OpenAI 릴리스 노트](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)의 2026-08-04 항목에서 10k자 초과 paste의 첨부 전환을 확인했다. 한 번의 이벤트를 4,000코드포인트(UTF-16 최대 8,000자)로 제한하고, CRLF 정규화 후 나누어 이모지와 개행 경계를 보존한다. 열린 clipboard slice와 표시용 마지막 BR을 사용해 조각 사이 문단 추가·개행 손실을 막는다. 최종 전체 내용 검증은 유지한다.

설정된 셀렉터는 Locator.evaluate / or / and로 처리해 CSS 외의 Playwright 셀렉터 문법을 유지한다. 격리 Chrome + ProseMirror에 10k 초과 paste를 가로채는 핸들러를 추가한 실험에서 동일 91,203자 입력 523ms, 내부 문서 원문 일치를 확인했다. `#prompt-textarea:visible`, `css=...`, XPath 전송 버튼 및 중지 버튼 제외도 통과했다. 회귀 테스트 92/92와 build 통과. 실제 로그인 서비스 검증은 여전히 남아 있다.

1. focus / insert 또는 paste / 내용 검증 / click / 전송 확인의 시작·종료 시간을 구분한다. 길이·줄 수와 page crash 이벤트도 기록한다.
2. 진행 중 생성이나 공유 브라우저를 끊지 않는다. 별도 테스트 환경에서 같은 크기의 입력으로 paste와 insertText를 비교한다.
3. paste는 반환값이 아닌 전체 입력 내용으로 검증한다. 대량 글자별 타이핑 제거와 버튼 대기 예산 통합을 우선 검토한다.
4. 고정 diff 전달을 조용히 생략하거나 자르지 않는다. 입력 최적화와 리뷰 대상 보장은 별개다.

### 2026-09-17: 구버전 실행 흔적과 입력 로그 정리

`osk-system#63` 상태 이력(KST)과 `data/watch.log`를 대조했다.

- 06:19:16, 06:20:23: 자동 재시도 두 번 모두 프로젝트 진입 실패. 원인이 두 번째 줄에 숨는 구형 문구였다.
- 두 문구는 `03b1ffa`(9/14) 이전 코드와 일치한다. 현재 코드는 해당 두 문구를 그대로 만들 수 없다.
- 06:28:50: 로컬 `dist/chatgpt.js` 재빌드. 06:29:46: 새 데몬 기동(`node --import tsx .../src/cli.ts serve --ui --no-open`).
- 06:30:22: 88,843자·1,626줄을 23조각으로 입력, 전체 검증 통과(1,530ms), 전송 확인 통과. 06:38:25경 응답 2,087자 수신 후 인라인 리뷰 3개 게시 완료.

전역 `pr-review`는 이 체크아웃에 연결된 npm junction을 통해 `dist/cli.js`를 실행한다. 백그라운드 클라이언트는 `src/cli.ts`를 우선한다. 따라서 소스 업데이트만으로 기존 빌드나 실행 중 프로세스가 갱신되지는 않는다. 업데이트 후 전역 명령을 쓰려면 `npm run build`하고, 기존 데몬도 라운드를 마친 뒤 재시작해야 한다.

구버전 실행은 오류 문구로 확인된다. 다만 종료된 프로세스의 명령줄과 실패 당시 입력 본문은 남아 있지 않아, 낡은 `dist`를 새로 실행했는지 이전 프로세스가 계속 돌았는지는 구분할 수 없다. 최초 불일치는 구버전의 URL 칩 변환/꼬리 개행 문제, 후속 진입 실패는 남은 입력을 초안으로 감지한 문제와 부합하지만 당시 DOM이 없어 세부 원인은 추정이다. `watch` → `serve`는 같은 명령 핸들러의 별칭 변경이므로 이 입력 오류의 원인이 아니다.

정상 입력은 길이·줄 수·조각 수·검증 통과·전체 소요 시간을 한 줄로 기록한다. 조각별 정상 시작/완료는 생략하고, 10초 지연 경고와 실패 단계(조각 번호 포함), 내용 불일치 진단은 유지한다. 전송 버튼과 전송 확인은 각각 완료 한 줄을 남긴다.

### 응답 대기 표시

기존 `화면 변화 없음`은 실제로 답변 본문만 비교했다. `osk-system#63`에서는 본문 0자여도 생성 중지 버튼이 보이고 생성 통신이 1~2초 전까지 관측됐으며, 약 8분 후 정상 응답을 받았다. 추론 중 UI 전체가 멈췄다는 증거가 아니다.

- 생성 표시는 있으나 본문이 없으면 `생성 중 · 본문 대기`, 본문이 나오면 `답변 수신 중`, 생성 표시가 사라지면 `완료 확인 중`으로 표시한다. 생성 표시도 본문도 없을 때는 추론 중이라고 추정하지 않는다.
- 정상 생성 통신이 확인되는 동안 정체 경고를 내지 않는다. 관측이 부족할 때만 답변 본문 미갱신과 통신 관측 한계를 명시하고, 같은 정체 구간에서는 한 번만 경고한다. 중지 버튼 상세 덤프는 타임아웃 때 남긴다.
- 일반 진행 로그는 상태가 바뀔 때 또는 2분마다 출력한다. 대시보드는 기존 3초 폴링 갱신을 유지하며 본문 대기 중 `0자 수신`은 생략한다.
- ChatGPT의 별도 생각 중 문구/애니메이션을 직접 감지하는 기능은 추가하지 않았다. 현재 연결된 브라우저에 생성 중인 ChatGPT 탭이 없어 실서비스 DOM을 검증하지 못했기 때문이다. 전체 화면 관측이나 추론 완료 판정으로 확대 해석하지 않는다. 완료·타임아웃 조건은 유지한다.
- `tests/response-progress.test.ts`에서 약 4분간 본문 없이 생성 통신만 있는 경우의 무경고, 통신 미관측 경고 1회, 본문 수신 후 정상 완료를 재현한다.
