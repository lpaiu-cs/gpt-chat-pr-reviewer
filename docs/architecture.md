# 동작 원리

[README로 돌아가기](../README.md)

이 문서는 사용 전에 반드시 읽어야 하는 안내가 아니라, 리뷰가 반복 실행되고
복구되는 방식을 이해하거나 개발할 때 참고하는 설명입니다.

## 전체 흐름

1. 감시 범위에서 PR과 GitHub 상태를 읽습니다.
2. 리뷰가 필요한 PR을 대기열에 올립니다.
3. ChatGPT 대화에 PR URL과 리뷰 지침을 보냅니다.
4. 응답 JSON을 파싱하고 변경 라인과 대조합니다.
5. GitHub 인라인 리뷰로 게시합니다.
6. 새 커밋이나 스레드 해결을 감지하면 다음 라운드를 시작합니다.
7. 더 지적할 내용이 없으면 수렴 상태로 끝냅니다.

## 리뷰 수명주기

| 상태 | 의미 | 다음 단계 |
|---|---|---|
| `REVIEW_DUE` | 리뷰 대기 | 대기열에서 선택 |
| `REVIEWING` | ChatGPT 리뷰 진행 중 | 게시, 수렴, 실패 또는 한도 |
| `AWAITING_AUTHOR` | 지적 게시 후 작성자 응답 대기 | 새 커밋 또는 해당 라운드 스레드 해결 |
| `CONVERGED` | 더 지적할 내용 없음 | 새 커밋이 생기면 리뷰 재개 |
| `QUOTA_BLOCKED` | ChatGPT 한도 도달 | 쿨다운 뒤 자동 재개 |
| `ERROR` | 라운드 실패 | 설정된 횟수만큼 자동 재시도 |
| `CLOSED` | PR 닫힘 또는 머지 | 종료 |

전이 규칙의 단일 소스는
[`src/state/machine.ts`](../src/state/machine.ts)의 `TRANSITIONS`입니다.

실제 리뷰를 시작하면 PR에 👀 반응을 남깁니다. 라운드가 끝나면 이를 제거하고,
지적 없이 수렴하면 👍 반응을 추가합니다. 새 리뷰가 필요해지면 이전 수렴 반응을
제거합니다.

## GitHub 상태 동기화

`watch`는 PR의 head SHA, 열림/닫힘, 리뷰 스레드 해결 상태를 주기적으로 읽어
내부 이벤트로 변환합니다. 프로세스가 중단되어 리뷰 중 상태에 남아 있어도 다음
동기화에서 복구할 수 있습니다.

스레드 resolve는 PR의 `updatedAt`을 갱신하지 않으므로, 작성자 응답을 기다리는
PR은 스레드 상태를 직접 조회합니다. 2차 라운드부터는 이전 지적의 해결 및 답변
현황을 프롬프트에 포함합니다.

## 응답 수집

응답은 **마지막 사용자 메시지 바로 뒤의 어시스턴트 메시지**에서 읽습니다. 이
위치는 폴링마다 화면에서 다시 계산합니다. 대화가 길어지면 ChatGPT가 화면 밖
메시지를 붙였다 떼기 때문에, 전송 시점에 센 메시지 수를 위치로 고정해 두면
응답이 화면에 다 나와 있는데도 아무 노드도 가리키지 못한 채 응답 예산
(`responseTimeoutMs`)을 모두 소진합니다.

대상 노드를 찾으면 메시지 식별자로 고정해 이후에는 같은 메시지만 읽습니다.
ChatGPT는 전송 직후 임시 식별자로 답 노드를 그린 뒤 서버 식별자가 오면 그 노드를
갈아 끼우므로, 고정한 노드가 사라지면 **같은 질문의 답인지 확인하고 따라갑니다.**
확인 기준은 그 답을 부른 질문입니다 — 답이 길어져 질문이 화면 밖으로 밀려나
기준점이 직전 턴으로 물러선 경우에는 따라가지 않고 라운드를 접습니다. 직전
라운드의 응답을 새 응답으로 게시하는 것이 가장 비싼 실패입니다.

전송 직후 우리 질문이 화면에 그려지기 전에는 아무 노드도 고정하지 않습니다.
그 순간 "마지막 질문 뒤의 답"은 직전 라운드의 답이기 때문입니다. 그래서 전송
직전의 마지막 질문을 기억해 두고, 화면의 기준점이 그것에서 넘어간 뒤에 고정합니다.
대상이 정해지기 전에는 어떤 노드도 읽지 않습니다 — 위치로 아무 메시지나 읽으면
그 값이 안정 관측을 통과해 그대로 게시됩니다.

## 중복 게시 방어와 숨긴 코멘트

같은 지적을 두 번 올리지 않습니다. 게시 직전에 **아직 열려 있는(미해결) 우리
지적**과 대조해, 파일·라인·본문이 모두 같은 코멘트는 빼고 올립니다. 남는 것이
하나도 없으면 리뷰 자체를 올리지 않고 그대로 작성자 응답을 기다립니다. 해결된
스레드는 대조하지 않습니다 — 닫힌 지적을 모델이 다시 든다면 그것은 "아직 반영되지
않았다"는 재지적이므로 게시되어야 합니다.

사람이 GitHub에서 **숨긴**(minimize) 코멘트는 없는 것으로 봅니다. 다만 주기적인
probe는 스레드의 해결 여부만 보므로 숨김을 감지하지 못합니다. `fullSyncIntervalMs`
(기본 10분)마다 PR 1건을 전체 조회해 이런 변화를 반영합니다. 리뷰 전체를
숨긴 경우 인라인 코멘트 자체는 숨김 표시가 되지 않으므로, 코멘트와 그 코멘트가
속한 리뷰를 함께 확인합니다. 숨긴 스레드를 계속 미해결로 세면 그 라운드는 전체
해결 판정이 성립하지 않아 응답 대기에서 빠져나오지 못합니다. 마지막 라운드의
지적이 전부 숨겨졌다면 화면에 남아 있는 직전 라운드가 판정 대상이 됩니다.

## 리뷰 대상 고정

리뷰가 진행되는 동안 PR에 새 커밋이 들어올 수 있습니다. 이 도구는 리뷰 요청
시점의 head SHA와 base ref를 저장하고, 게시하는 GitHub 리뷰도 그 커밋에
고정합니다. 검토하지 않은 새 커밋이 수렴으로 잘못 기록되지 않도록 하기
위해서입니다.

## 대기열

브라우저 페이지가 하나이므로 리뷰는 직렬입니다. 각 스캔은 전체 대상을
동기화한 뒤 대기열에서 한 건만 실행하고 다시 스캔합니다.

기본 우선순위는 다음과 같습니다.

1. 아직 한 번도 리뷰하지 않은 PR
2. 작성자가 응답한 PR
3. 재시도나 그 밖의 리뷰 대기 PR
4. 같은 순위에서는 오래 기다린 PR

대기열은 별도 파일로 저장하지 않고 현재 PR 상태에서 매번 계산합니다. ChatGPT
한도에 걸려도 버리지 않으며 쿨다운 뒤 같은 우선순위로 재개합니다.

## 하나의 데몬과 브라우저

여러 에이전트 세션과 CLI 요청은 하나의 watch 데몬에 연결됩니다. 데이터
디렉터리마다 루프백 포트 잠금을 사용해 두 번째 데몬이 동시에 같은 상태를
수정하지 못하게 합니다.

- 비용을 발생시키는 `review` 요청만 필요할 때 데몬을 시작합니다.
- 읽기 전용 상태 조회는 데몬을 임의로 시작하지 않습니다.
- 감시 범위는 전역 설정이므로 에이전트 스킬이 자동으로 넓히지 않습니다.
- 정상 종료는 현재 라운드를 마친 뒤 이루어집니다.

별도 MCP 서버 대신 얇은 스킬 클라이언트를 사용하는 이유도 같습니다. 세션마다
MCP 서버를 실행하면 결국 같은 데이터와 브라우저를 두고 경쟁하므로, 공유
데몬이 직렬화 지점이 됩니다.
